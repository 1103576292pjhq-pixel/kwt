# 验收方法

1. 使用真实 E203 执行 `red_stub.c`，让 main 返回 -77。正常验收必须因 `CPU_EXIT_FAILURE` 非零退出，证明 BOOT 魔数本身不等于成功。
2. 同一固件驱动运行 M=3、N=4、K=64，使用 Icarus 及 Verilator 分别执行。逐项输出、flags 和完整文件哈希必须一致。
   再对验证环境复制出的参考答案翻转一位，保持 CPU 输入、固件和 RTL 不变，必须在 CPU 写回第 0 项时非零拒绝。
3. 默认 M=99、N=256、K=64，运行真实参考向量中的首个完整案例。CPU 必须实际完成 22,976 次装载提交、一次 START、99 次顺序 ACK，写回全部 25,344 项数值和 flags。
4. testbench 被动观察系统 ICB 写口，逐项比较输出及 flags；CPU 完成后再逐项检查共享 SRAM。Python 再独立解析全部索引与数值，不能用单一校验和代替输出比较。
5. 在新的仿真进程重跑完整案例。数值、flags、周期、指令计数和输出文件哈希必须一致。
6. 确认依赖及所有生产源运行期间未变，官方上游树仍符合源清单后才发布 PASS。

完整案例的 M×64+N×64+N = 6,336+16,384+256 = 22,976 次装载提交由 CPU 执行；单 MAC 实际计算 1,622,016 次乘法。小矩阵只用于快速联调和仿真器交叉验证，不替代完整尺寸案例。

运行失败会使 `result.json` 和 `work/e203_ffn1_handoff.json` 成为 FAIL；运行开始先写 RUNNING，防止把旧 PASS 当本次结果。`commands.jsonl` 保存命令、工作目录、真实退出码、墙钟耗时和日志哈希。完整仿真不转储巨大波形，而保存 CPU 阶段、行 ACK、事务计数和全部结果文件。
