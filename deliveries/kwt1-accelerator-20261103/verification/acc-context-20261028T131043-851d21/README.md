## TB怎样检查

测试文件为 `tb/compute/tb_acc_context_bank.v`。在下降沿送入数据，上升沿之前检查输出不应变化；在上升沿后等待非阻塞赋值更新，再检查block_done，并依次改变rd_addr读取全部64个acc。选读之间等待10ps用于组合逻辑稳定，64次读取在下一个时钟沿前完成，不要求被测电路真实具有多端口同时读出能力。

参考数组使用64位有符号整数按ctx/行/列保存期望，输入32位乘积先按有符号解释再累加。该参考不读取DUT内部acc，只通过公开rd_acc比较，使用四态比较检出意外X。第一次clear前acc允许未知；clear后每拍均检查所有64项，包括未被更新的上下文及屏蔽行。

控制检查包括：复位优先于clear、clear优先于有效乘积；未clear时不接收数据；无效输入和无效last不更新或完成；最后一组写入与完成脉冲对齐；完成后锁住结果；中途同步复位后必须重新clear；连续新块不继承旧和。短事务与故意的清零冲突属于组件控制压力，不宣称是合法完整矩阵调度。

## 数据从哪里来

没有下载音频或权重，也没有改动或使用DEV12黄金来迎合RTL。全部刺激直接由TB构造。

10个完整块分别是：全零、可手算4×16块、仅k63非零、64项最大正乘积、64项最大负乘积、正负前缀抵消，以及4块随机数据；最后一块mask=0111，前三行参与累加。每个k复用四个X，并使用16列W依次形成四个g，符合4×4外积/CTX4结构。随机数使用Icarus `$random`，初始种子20261028；随机算法与工具实现有关，已保存的实际输入才是本轮精确数据身份。

独立字面锚点包括：

- 手算块仅k0非零，X[p,0]=4096×(p+1)，W[0,c]=16×(c+1)，因此acc=65536×(p+1)×(c+1)。这里检查的是加bias之前的Q28编码，不是最终Y。
- 最大正和：64×((-32768)×(-32768))=68719476736。
- 最大负和：64×((-32768)×32767)=-68717379584。
- 32个负乘积和32个正乘积抵消，最终为0；逐拍扫描仍检查中间大前缀，避免只检查最终0。
- 只有k63非零的第一个输出为(-4096)×96=-393216，检查最后贡献不丢失。

此外，TB末尾使用signed32最小值做单项符号扩展压力；这是额外组件输入，不声称可由signed16×signed16乘法产生。

## Python黄金怎样对照

TB将10个块实际使用的X/W和最终64个acc写入 `acc-trace.txt`。脚本 `scripts/verify_acc_context.py` 解析该文件，重建每块X[4,64]与W[64,16]；依据地址ctx×16+p×4+q找出对应行列，对每个输出调用原有 `model.fixed_numeric.dot64_scalar(x,w,0)`。

因为bias=0且合法K64不触发sat40，该函数返回的raw等于量化前的完整点积和，与硬件rd_acc直接比较。尾行组被屏蔽的第4行期望为0。总计640项，不使用TB参考数组生成Python期望，也不把舍入后的Y反推成acc。

## 检查TB确实会报错

脚本只在本验证目录生成6个错误副本，不改生产RTL：乘积高位补0、选错上下文旧值、忽略行mask、跳过最后一组、忽略active、clear漏掉第63项。它们均成功编译，再由TB因数值或时序不符以退出码1停止。各错误的命令、报错拍和地址保存在mutant日志中。这是针对性检错，不是形式证明或完整故障覆盖率。
