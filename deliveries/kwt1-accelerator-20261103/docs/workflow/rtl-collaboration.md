# RTL协作与记录流程

2026-10-31新增优先规则：[仅以赛方资料作为外部设计依据](design-sources.md)。停止使用交接包及其衍生协议作为设计来源；此前文档中的兼容性取舍不自动约束后续实现。

更新：2026-10-29。依据用户在本对话明确说明的学习方式，适用于点积核和后续整个加速器。旧交接词中的“继续实现”表示总体目标，不代替下面逐模块理解和讨论的过程。

## 1. 我们怎样写RTL

```text
用户讲想法 → 助手补充/纠正并解释原因 → 形成共识 → 写入工程
    ↑                                                   ↓
    └──── 讨论修改 ← 用户阅读代码并提出优化 ←───────────────┘
                          ↓
                    按要求验证与总结
```

1. 开始模块前，先说明它解决什么问题、与已有模块怎样连接、哪些职责归外围。
2. 用户先提出输入输出信号、中间逻辑以及组合/时序划分。存在遗漏或错误时，助手解释原因，配合小段`.v`代码、具体数值和时钟沿例子。
3. 达成共识后，助手直接编辑当前工程的实际文件并用VS Code打开，不用聊天中的代码或下载包替代工程修改。
4. 用户阅读后提出简化或优化。助手独立判断其正确性，解释功能、时序、资源方面的影响，再落实合理修改；不机械顺从，也不因变量暂时难懂就删除必要控制。
5. 讨论和优化可反复进行。用户说“先不用验证”时先供阅读；要求验证后再写TB、编译、运行、记录结果。
6. 验证总结包括测试方法、实际数据来源、黄金生成方式、命令和退出码、覆盖范围与剩余边界。

## 2. 每个模块开工前讲清什么

| 项目 | 需要回答的问题 |
|---|---|
| 责任 | 本模块负责什么？已有模块是否已经实现同一职责？ |
| 接口 | 信号方向、位宽、signed、尺度、打包顺序是什么？ |
| 接收 | valid/ready在哪个时钟沿成交？是否允许空拍、连续输入？ |
| 保存 | 哪些数据、标签和进度必须跨拍保存？ |
| 计算 | 哪些组合并行完成，哪些依靠寄存器逐拍推进？ |
| 完成 | 是输入收完、最后写回、结果交付，还是CPU确认？ |
| 复位 | 哪些寄存器需要清除？旧在途数据如何隔离？ |
| 验证 | 手算锚点是什么？最容易错的边界是什么？ |

## 3. 代码与资料习惯

- 生产RTL使用Verilog `.v`，公共宏使用`.vh`，中文注释、UTF-8；不得随意改变已冻结的算术和架构。
- 有真实需要再增加中间变量；保留必要的符号扩展、位宽和标签控制。
- 先读取当前磁盘文件再编辑，保护用户修改。历史报告和旧工程不覆盖、不清理成“只剩PASS”。
- 对新写法可比较多个成熟GitHub实现，记录出处、适用条件与本工程差异；不能把不同数值合同直接搬入，也不凭参考代码声称本工程已验证或PPA最优。
- 口头优化中的资源/速度收益若没有综合、STA或周期测量，只写“预期/待测”。
- `timescale`用于仿真时间解释，不能作为频率约束；是否添加与是否可综合分别判断，见[基础笔记](../learning/rtl-basics.md)。

## 4. 怎样把过程留下来

每个模块用一份[模块开发记录模板](../rtl/module-record-template.md)。一次讨论结束后，把四件事写到对应模块记录中：

1. 用户的想法和问题（概括或准确引用，不能虚构原话）。
2. 助手补充了什么、为什么，必要时保留最小代码或逐拍表。
3. 最终采用什么方案，代码或接口实际改在哪里。
4. 验证到什么程度、对应哪个报告；未验证的部分明确保留。

一般知识沉淀到learning；跨模块设计选择放architecture；接口及系统联调放rtl/accelerator；仿真原始证据留verification。模块记录引用这些资料，不复制整份黄金、接口表或日志。

## 5. 换对话时

先读本文、[实现进度](../implementation/progress.md)、[模块记录索引](../rtl/README.md)和当前阶段交接词。确认上一轮用户正处于“讨论、阅读、优化、待验证”的哪一步，再继续；总体推进授权不表示可以跳过用户希望参与的思考过程。
