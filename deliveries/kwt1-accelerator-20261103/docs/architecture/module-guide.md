# 从头理解本科加速器：数据、控制和每个模块的原因

配套规格：[README](README.md)。本文讲解修订后的目标架构；原交接包代码仍是48位，不能把本文当作已完成的RTL。

## 1. 先分清五个概念

- **数据通路**：X/W从存储到乘法、累加、量化、结果块的路径。
- **控制通路**：决定何时读写、用哪个槽、累加哪个上下文、何时发布或结束。
- **bank**：可以独立使能的存储分体。四个bank可同拍各读一项；一个SP bank本身仍不能同拍完成任意读写。
- **slot/owner**：某份存储目前归哪个任务/阶段使用。owner没有释放前不能覆盖，即使其中某些数已经读过。
- **ready/valid**：一拍中两者都为1才发生一次传输；valid为1但ready为0时，相关数据与身份必须保持。

同一条命令有三个时点：被接口接受、被核心实际执行、响应被接收。队列与桥把它们分开；把三者当同一拍会造成重复执行或过早完成。

## 2. 任务和数据在哪里

外部量化工具准备X[99,64]、W[64,256]、bias[256]，CPU从共享RAM读它们。内部X/W是为了高带宽复用而保存的另一份局部数据，不是CPU直接执行矩阵乘法。

| 共享对象 | 排列 | 容器大小 | 为什么 |
|---|---|---:|---|
| X | row×64+k，行主序 | 12672 B | 一行的64项连续 |
| W | col×64+k，列主序 | 32768 B | 保留交付数据布局；驱动发布时重排为k/列对 |
| bias | 每列一项，int64容器 | 2048 B | 兼容共享描述符/驱动，合法数值仍signed32 |
| Y | row×256+col，int32容器 | 101376 B | CPU32位读写，内部sat16符号扩展 |
| flags | 与Y同索引，每项uint8 | 25344 B | bit0/1/2有效，其余补0 |

五个数据对象共174208 B，描述符、mailbox、对齐、G占用另算。任务描述符含task、layer、shift、X/W/bias/Y/flags各偏移，共八个32位字；它没有动态矩阵尺寸字段。

共享bias若出现超出signed32的int64值，软件必须在丢弃高位之前拒绝。RTL只能校验到达它的48位，无法识别已经被软件截掉的bit63..48。

## 3. 输入wrapper：为什么核心前面还要接口层

原包对应 `revd_opt_icb_w2`。CPU按地址读写寄存器，计算核理解BEGIN、X、OPEN等有顺序的事件，wrapper负责二者转换、缓冲和响应保持。

META保存op/layer/shift，TASK保存任务，POSITION保存tile/index，DATA_LO/HI拼成legacy数据。CPU写COMMIT寄存器0x18才把当前暂存内容快照入FIFO；仅写暂存寄存器不会写X/W或启动计算。

FIFO每项保存pair标记、meta/task/position、原始data48。保留data48用于ABI兼容和完整的signed16/signed32合法性检查。八项并不等于八拍全部执行完成：pair最多还包含两个标量，核心q也可能等待W槽。

PAIR_NEXT一次写入两个16位数，低半先执行、高半后执行。FIFO的input_half只记录当前处理哪一半；低半握手只切half，高半握手才真正出队。成功入队时position低16位+2，和核心何时执行这对数据是两件事。

## 4. 命令从BEGIN到START

| op | 名字 | 含义和原因 |
|---:|---|---|
| 0 | BEGIN | 绑定新task/layer和固定shift16，清进度；防止新旧任务混用 |
| 1 | X | 必须按index0..6335装完整X，检查signed16 |
| 2 | OPEN | 申请FREE的W槽，并声明准备装哪个tile |
| 3 | W | 当前tile内依次装1024项，防止缺项/乱序 |
| 4 | bias | W齐备后装16项；检查signed32后保存 |
| 5 | COMMIT | 表示W+bias完整，把槽从LOADING变为READY |
| 6 | START | 首tile提交后开始矩阵任务；整项任务只发一次 |

顺序是BEGIN→X全量→OPEN0→W0/bias0→COMMIT0→START，再装其他tile。OPEN之后必须重设PAIR_NEXT位置锚点，因为OPEN本身使用同一组legacy暂存寄存器。

两个W槽都占用时，合法OPEN等待；缺参数、错误tile、错误顺序或非法值应报错，不能全部伪装成“还没ready”，否则错误输入会永远等下去。

原包把这些进度、槽和计算状态多放在同一核心模块中。这里按职责讲解不意味着要求你机械地新建同数量的RTL模块。

## 5. X四bank与W双槽为什么这样分

计算每拍需要四行X、四列W。X按row%4分bank，所以同一行组的四行不会争用一个端口；W按tile内col%4分bank，所以同一列组的四列也可同时读。

X[5,7]进入bank1，地址floor(5/4)×64+7=71。W在某个tile内的c13/k7进入该槽bank1，地址floor(13/4)×64+7=199。

X每bank1600=25行组×64，四bank容量6400项，实际使用6336项；最后四行组位置中有一行无效，不能读取其未装载数据。W每槽四bank×256项=1024项=64×16。

W槽的FREE→LOADING→READY→ACTIVE→FREE分别表示可覆盖、正在写、写完待算、正在使用、依赖全部结束。双槽让一个读另一个写，既满足单端口限制，也隐藏部分装载时间。只把“忙”设一位无法区分这些阶段。

## 6. 计算核：一个输出到底怎么得到

对tile t、行组row0、上下文g、块内行p和块内列q：

`acc[g,p,q] += X[row0+p,k] * W[k,16*t+4*g+q]`。

p和q各0..3，共16个乘法；g0..3共四组独立累加状态，合计64个输出。四上下文解决16条乘法通路分时覆盖16列的问题，不会把四个g的和再加成一个输出。

每个k的顺序是g0→g1→g2→g3，随后k++。g0读X并保留x_hold，后三组复用X；每组读新的W。64个k共256次请求。

L1简化时序：

| 时刻 | SRAM请求 | 返回数据形成乘积 | 旧乘积累加 |
|---|---|---|---|
| e0 | k0/g0 | 无 | 无 |
| e1 | k0/g1 | k0/g0，同时保存X | 无 |
| e2 | k0/g2 | k0/g1，复用X | k0/g0 |
| e3 | k0/g3 | k0/g2 | k0/g1 |
| e4 | k1/g0 | k0/g3 | k0/g2 |

每份数据都带valid和k/g/mask/task/row/tile/slot标签。不同流水阶段的“当前k”可能不同；请求计数不能直接拿来选择刚返回的结果。最后请求发出后仍有返回和乘积在路上，FLUSH等它们真正累加完。

## 7. 核心状态机每一段为什么存在

| 状态 | 工作 | 少了会怎样 |
|---|---|---|
| IDLE | 无计算，等待合法新任务 | 无法划分任务边界 |
| LOAD | 初始装载X及首W槽 | 未装全就计算会读旧数据 |
| CLEAR | 清当前64个acc | 不同输出块的和混在一起 |
| RUN | 发256次读请求并流水处理 | 这是主要乘加阶段 |
| FLUSH | 排空最后请求/乘积 | 漏k63最后一组贡献 |
| ALLOC | 等空结果owner | 覆盖CPU尚未处理的旧结果 |
| QISSUE | 选一个acc/bias，交给量化器 | 没有明确量化输入接受边界 |
| QWAIT | 等量化结果成功写入payload | 输出背压可能丢项或重复推进 |
| PUBLISH | 整块写完才对CPU可见 | CPU可能读到半块数据 |
| WAIT_TILE | 等下一tile READY | 读到尚未装好的W |

QISSUE/QWAIT使用同一份量化器，按当前结构交替服务单项结果。保留这一结构是限制资源与实现改动的选择；是否值得进一步重叠，要另有测量依据。

## 8. 量化器：为什么有加宽、右移和饱和

X/W分别有12/16个小数位，乘积自然有28个小数位。bias也必须Q28，否则直接相加相当于单位不同。输出目标Q12，所以丢掉16个小数位，右移量由28−12推导。

acc40和bias32先分别符号扩展到41位相加，额外一位用于检查越过40位范围。这里的41位是局部加法临时量，和把全部acc长期存为48位性质不同。raw钳到40位后按RNE/sat16得到Y。

例：bias=163840，其他乘积0，则除65536为2.5，RNE取2；bias=229376对应3.5取4；负数分别取−2、−4。bias=2147483647舍入后为32768，sat16得到32767，saturated=1；bias=−2147483648正好得到−32768，saturated=0。

overflow与saturated不同：前者是raw加法越过40位，后者是舍入后越过16位。合法整任务overflow应一直0，但saturated可以为1。last由全局坐标生成，不由量化数值决定。

固定shift16的手算4×16例：仅k0非零，X[row0+p,0]=4096×(p+1)，W[0,c]=16×(c+1)，bias0，其他k补零。输出编码Y[p,c]=(p+1)(c+1)，无饱和。尾组三行只产生48项。该例无需生产入口接受shift0。

## 9. 双结果块：为什么需要owner、mask和描述符

结果项是y16+overflow+sat+last，共19位。每块64项，两个块共304 B payload；未存完整99×256 Y。复制量化结果后，acc可清零用于下一块，CPU可晚些读取旧块。

量化按g、row、col枚举，填入地址row×16+g×4+col。例如先写0..3，再写16..19，未按0..63顺序完成。仅有fill_count不能发现“重复写一项、漏另一项”，所以written_mask用64位分别记录每项是否已写。

descriptor中的row/tile决定结果属于哪里，count区别64/48，task隔离任务，sequence辨别块与旧ACK。一个普通块内cursor从0到63，尾块到47；count和cursor需要能表示64，不能都只用6位。

CPU读出index=(row+cursor/16)×256+tile×16+cursor%16。例如row4/tile2/cursor17对应Y[5,33]，全局index1313。只有最终tile15、row96、cursor47对应Y[98,255]，last=1。

## 10. 读结果、ACK与两级响应

1. CPU发RESULT，经guard转给B wrapper。
2. 结果队列接受读命令，把当前项快照进响应寄存器；cursor暂不动。
3. 本地B响应valid&&ready成功时，队列cursor只前进一次。整机中接收方是guard，guard保存返回值。
4. guard等待CPU接收它的上游响应；这期间不接另一条请求，也不再次执行刚才的RESULT。
5. CPU把Y32/flags写共享RAM，整块写完fence，再ACK。
6. ACK匹配task/sequence/count且已读完时，队列接受沿释放owner；ACK后续响应仍必须被guard/CPU排空。

因此“响应被谁接收”必须指明接口。独立B测试可直接背压B响应；真实SoC里也可能是guard先收下B响应，再替CPU保留。两者都要求不重复消费，但不能把cursor更新硬绑到CPU最终rsp_ready。

## 11. CPU驱动为什么属于架构理解的一部分

因为CPU既送输入又收输出。若CPU只等FIFO空位，不读结果，就可能出现：两结果块满→核心停ALLOC→当前tile无法publish结束→W槽不释放→OPEN堵住→FIFO不腾空。等待输入时同时drain结果才能打破这个环。

F3仍逐项校验任务、范围、duplicate、保留位和global-last；每四项共用一个seen位图字读写，组间递增索引。四项flags用一次32位写是已有输出组织，不能全算作F3新增。Y仍逐项写32位，RESULT读事务数不减少。

软件返回错误不等于输出原子回滚：此前写过的Y可能保留，当前组也可能只写了部分Y，不能把失败任务当作完整结果。真实MMIO总线陷阱与普通C错误码也不同。

## 12. guard为什么不能简单用busy取反代替

计算busy=0时，还可能有FIFO命令、RAM读返回、量化输出、未ACK结果、B响应、guard响应或共享RAM写响应。quiet检查这些状态是否真正排空。

BEGIN打开session并分配task；COMPLETE要求端点done、全部安静、epoch/task token匹配；模式切换要求任务已封闭且无在途工作。epoch区分恢复/模式代次，task区分任务，sequence区分同任务的结果块，三者各有不同作用。

ABORT可以取消算术，但不能丢掉已接受请求的响应。flush后只清所有权和valid，数据RAM不逐项复位，旧字可以存在但不得被当成新数据读取。

## 13. MMIO地图：每组寄存器为什么存在

B基址0x11000000，四字节对齐，写mask=0xf。下表保留原ABI，数值合法性按新规格收紧。

| 偏移 | 作用 | 原因 |
|---|---|---|
| 00 | STATUS：FIFO未满/可读结果/端点done/fault | CPU服务与错误检查入口 |
| 04、08、0c | META、task、position | 命令的类型、身份、位置 |
| 10、14、18 | data低32、高16、legacy发布 | 保留原命令容器，最后一次发布原子快照 |
| 1c、20、24、28、2c | legacy索引/Y/flags/task/POP | 兼容旧结果读取方法，使用同一队列 |
| 30 | 错误码 | 区分非法命令与结果生产错误 |
| 34、38 | 已接受标量数、已POP/ACK项数 | ABI诊断计数，不能与计算完成混用 |
| 40 | 结果能力标识0x08010002 | 驱动识别结果协议 |
| 44 | 块有效/fault/compute_done/读完 | 区分发布、消费、整体完成 |
| 48、4c、50 | row/tile/count、task、sequence | 每块共享身份，无需每项传完整索引 |
| 54、58 | packed RESULT、ACK | 逐项消费，整块释放 |
| 5c | FAST_ENABLE | 在安静边界选择兼容/快速结果协议 |
| 60、64、68 | pair能力、FIFO容量/half、PAIR | 双16位发布与容量可见 |
| 6c、70 | auto能力、PAIR_NEXT | 自动位置更新 |

这些能力ID描述接口，不能仅凭同样CAP值就推断数值格式相同；构建交接还需绑定规格ID、固件和输入身份。当前8深度编码不可在改深度时随便沿用。

共享RAM基址0xa0000000；G窗口0x11010000；guard窗口0x11020000。guard的BEGIN/COMPLETE与B命令BEGIN不是同一层：前者打开系统任务，后者初始化B计算会话。

## 14. 一个完整任务按什么顺序结束

99行25组，256列16tile，共400块；每tile24块×64+尾块48=1584项，总25344项。X/W/bias及控制命令合计23010个标量事件；pair装载后实际FIFO入队项11650。这里是本配置无重复/重试的逻辑事件数，不等于MMIO事务总数或时钟周期。

计算tile t时CPU可装tile t+1，同时读取更早发布的结果。当前块MAC排空→量化→publish后推进下一行组；tile尾块publish后释放W槽并等下一tile。最终publish只表示计算生产结束；所有结果读写/ACK后B端点done，再排共享响应和guard响应，最后才能COMPLETE。

单笔共享通道和CPU服务速度仍能限制整机；本架构不承诺16个乘法器在整个冷窗每拍都工作。组件周期、整机冷窗、ACK/COMPLETE尾部、实际频率与功耗必须分别测量。

## 15. 看任何一段RTL都应能回答的问题

这个寄存器保存哪份数据或哪种进度？合法范围是什么？何时写、何时读、何时释放？valid或owner在哪里？背压时谁保持？非法输入怎样报告？复位/ABORT会不会吞已接受事务？这段逻辑是否改变数值、顺序或完成边界？

如果没有答案，先回到规格补齐，再写对应RTL。知道一个机制解决什么问题、删除后哪种情况会错，才算理解它；记住模块名和状态编号还不够。
