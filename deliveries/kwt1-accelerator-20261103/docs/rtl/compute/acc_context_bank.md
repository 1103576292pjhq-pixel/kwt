# acc_context_bank：四上下文累加开发记录

整理：2026-10-29。源码：[acc_context_bank.v](../../../rtl/compute/acc_context_bank.v)。

## 背景与用户思路

用户提出：接收乘积有效、各类标签和乘积结果，用时序逻辑累加，收到块的最后一组后输出结果及标签。

讨论补充：本模块保存四组独立上下文，每组4×4，共64个acc；不同ctx不混加。它提供完成脉冲和按地址选读，最终Y及全局标签由顶层/量化器处理，并非在最后一沿把所有结果压成一个输出。

## 接口与地址

| 接口组 | 含义 |
|---|---|
| clear | 同步清零全部64个acc并开始新块，优先于正常累加 |
| in_valid/in_product | 一组16个signed32乘积，共512位 |
| in_ctx/in_row_mask/in_block_last | 上下文、有效行和本块最后一组 |
| block_done | 最后一组实际写入后的单拍完成标志 |
| rd_addr/rd_acc | 6位地址选64项，组合输出signed40 |

```text
乘积lane = p*4+q
acc地址  = ctx*16+p*4+q
```

6位地址宽度表示能选择64个位置，不表示acc数值只有6位。每个值仍是40位Q28。

## 运算与时序

```verilog
assign lane_sum[LANE] = acc[write_addr] + product_ext;
```

product_ext把signed32乘积扩展为signed40。generate描述16条组合加法通路，当前ctx的有效行在同一上升沿写回16个位置；其余ctx和无效行保持。

正常使用顺序：复位关闭活动状态 → clear清零并令active=1 → 接收乘积 → 最后写回并产生block_done、active=0 → 保持结果供组合选读 → 下一次clear。

最后写回和block_done同时在沿后更新；下游在后续上升沿使用结果。clear必须在旧流水排空、新乘积尚未到达时发生。

## 讨论与优化记录

| 用户问题/建议 | 最终处理及原因 |
|---|---|
| 是否底层有16个加法器 | RTL描述16路并行加法；确切器件和资源数需综合确认 |
| 时序for是不是每拍只能写一个结果 | 固定for在同一个沿更新多个不同位置，不自动变成多拍循环 |
| 为什么有old_acc | 它原本只是组合读别名；按用户要求删去，直接读取acc，不改变运算 |
| generate和过程for是否一样 | 前者展开独立结构，后者描述过程内重复操作；这里均用于并行硬件描述 |
| active有何作用 | clear后才允许写入，完成或复位后关闭，防止在途/多余输入改坏保存结果 |

## 数值与控制注意点

- 64项signed16乘积的合法前缀严格在signed40内，普通40位加法与合同中的前缀sat40等价；不据此改回48位或缩窄冻结位宽。
- 本组件信任in_block_last，不自行重数256组；完整有序计数由顶层负责。
- 没有ready，活动块每组有效乘积都要接收。
- 复位不清大数组；复位后必须重新clear，未清零的旧数据不能作为新结果。
- 删除组合别名不意味着证明节省面积；lane_sum仍表达读取旧值后形成新和。
